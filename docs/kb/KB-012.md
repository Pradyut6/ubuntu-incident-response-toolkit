# KB-012 — Service dependency prevents startup

**Audience:** Ubuntu help desk, support and Linux operations  
**Status:** Written runbook; validation pending in an isolated Ubuntu VM  
**Associated scenario:** [INC-012](../../lab/incidents/INC-012.md)

## Customer-visible impact

Training application cannot start while its required dependency is absent. Treat impact and priority as simulated until an actual case is measured.

## Common hypotheses

- **Training cause:** Two isolated systemd training units with Requires/After; only test services are affected.
- Alternative causes might include service startup order, wrong bind address/port, ownership, AppArmor, incorrect configuration, missing dependency or unavailable system resources, depending on the component.
- Do not assume the simulated root cause from the symptom alone.

## Triage playbook

Run only the diagnostics relevant to this component and collect actual stdout, timestamps and exit codes. Recommended checks:

```bash
systemctl list-dependencies uir-training-012.service
systemctl status uir-training-012.service --no-pager
journalctl -u uir-training-012.service -n 40 --no-pager
```

Confirm the configuration/behavior against expected service contracts, correlate the error with the journal's unit, boot ID and UTC window, and retain a bounded before snapshot. If the suspected source is missing or inaccessible, record partial evidence rather than guessing. Investigate the earliest meaningful error, not just the latest restart attempts.

## Fix and verification

**Safe training remedy (VM only):**

```bash
sudo tee /etc/systemd/system/uir-training-dependency.service >/dev/null <<'UNIT'
[Unit]
Description=UIR dependency practice prerequisite
[Service]
Type=simple
ExecStart=/usr/bin/sleep infinity
UNIT
sudo systemctl daemon-reload
sudo systemctl start uir-training-dependency.service
sudo systemctl start uir-training-012.service
systemctl is-active uir-training-012.service
```

**Verification gate:** Required unit is loaded and running, dependent unit starts, and cleanup removes only training files.

Before labeling resolved, capture an after snapshot, rerun the functional check, compare relevant structured metrics and explain whether the evidence supports the hypothesized cause. A healthy `systemctl` status by itself might not verify the user's endpoint or application behavior.

## Prevention and handoff

Document the first timestamp seen, incident severity and customer update, exact corrective action, follow-up checks, changes to prevent recurrence, and knowledge gaps. Redact internal addresses, identities and credentials before sharing. Never mislabel a local simulation as a real customer outage.
