## User acceptance commands (run from Linux filesystem as regular user)

```bash
sudo apt update && sudo apt install -y jq shellcheck shfmt bats
bash -n bin/uir lib/*.sh tests/smoke.sh tests/integration/m3-store.sh
bash tests/smoke.sh
bash tests/integration/m3-store.sh
bats tests/unit
shellcheck -S warning bin/uir lib/*.sh tests/smoke.sh tests/integration/m3-store.sh
shfmt -d -i 4 bin/uir lib/*.sh tests/smoke.sh tests/integration/m3-store.sh
./bin/uir doctor
```

Then run `./bin/uir init`, `./bin/uir incident create ...`, `./bin/uir incident show ...`, and `./bin/uir incident list`. `init` may create a real private store under your home; the test scripts use their own disposable data directory.

## Security boundaries and outstanding work

- Settings describe future policies only. No pruning, quotas, evidence or compression at M3.
- No data file is auto-published to GitHub, no service is restarted and no fault is injected.
- The CLI validates paths and symlinks; shell-level checks are not a complete defense against filesystem races by an adversary already able to mutate the same-UID data directory.
- Data is not currently encrypted at rest. Avoid sensitive summaries and any genuine customer data.
- M4 implements read-only, bounded host diagnostics. M1 VirtualBox/snapshot acceptance remains separate and must pass before fault-injection scenarios.

## Next step

After user-side M3 checks pass, implement M4 host-health collectors with bounded runtime and output size; avoid service fault injection until the isolated VM baseline has been confirmed.
